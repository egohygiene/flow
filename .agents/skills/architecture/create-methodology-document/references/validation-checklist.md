# METHODOLOGY.md Validation Checklist

## Specification

- [ ] `architecture-methodology` is identified as the governing specification.
- [ ] The applicable specification version is known.
- [ ] Required upstream purpose, principles, foundations, and architecture documents have been read.

## Primary Question

- [ ] The document clearly answers:
      How does this project intentionally move from ideas to validated outcomes?

## Boundaries

- [ ] The methodology is a durable operating method rather than a task list.
- [ ] Validation and feedback loops are explicit.
- [ ] Repository structure, roadmap commitments, and CI implementation detail do not replace methodology.
- [ ] Human and AI collaboration patterns are included only when architecturally durable.

## Evidence

- [ ] Workflow stages are grounded in observable practice or accepted intent.
- [ ] Assumptions are labeled.
- [ ] Missing evidence is acknowledged.
- [ ] Contradictions between stated and actual method remain visible.

## Durability

- [ ] The method remains useful across tooling changes.
- [ ] Temporary habits are not normalized into permanent architecture.
- [ ] A contributor could repeat the method without reading chat history.

## Completion

- [ ] Acceptance criteria from `architecture-methodology` pass.
- [ ] Downstream review implications are recorded.
- [ ] Markdown, links, and metadata pass repository checks.
