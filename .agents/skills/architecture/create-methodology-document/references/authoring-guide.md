# Create Methodology Document — Authoring Guide

## Primary Question

    How does this project intentionally move from ideas to validated outcomes?

## What This Document Owns

- durable stages of work
- validation loops
- feedback and refinement cycles
- repeatable human and AI collaboration patterns
- the operating model for improving work over time

## Keep These Elsewhere

- `ROADMAP.md`: strategic sequencing and future horizons
- issue trackers and sprint plans: current task commitments
- CI config and runbooks: implementation of automation
- `ARCHITECTURE.md`: repository or system structure

## Strong Output Characteristics

- finite, comprehensible stages or loops
- explicit validation points
- durable enough to survive tool changes
- clear distinction between method and schedule
- honest about where practice is still evolving

## Common Anti-Patterns

- turning methodology into a weekly checklist
- equating the methodology with a specific CI pipeline or bot setup
- confusing roadmap phases with workflow stages
- documenting every temporary ritual as if it were a stable operating model

## Review Questions

- Can a contributor explain how work moves through the system?
- Are validation and learning loops explicit?
- Would the method still make sense if tooling changed?
- Is any backlog, release plan, or architecture content leaking in?
- Are unresolved process contradictions visible instead of hidden?
