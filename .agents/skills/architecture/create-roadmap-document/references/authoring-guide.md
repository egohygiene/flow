# Create Roadmap Document — Authoring Guide

## Primary Question

    How should this project evolve over time?

## What This Document Owns

- strategic initiatives
- capability evolution
- major phases or horizons
- long-term priorities
- future architectural direction when strategically relevant

## Keep These Elsewhere

- issue trackers and sprint plans: tactical task management
- release notes: historical shipment record
- `ARCHITECTURE.md` and `SYSTEM.md`: present-state canonical structure
- `METHODOLOGY.md`: how work gets done

## Strong Output Characteristics

- organized around capabilities and outcomes
- readable at a glance
- uses horizons rather than overcommitted dates when possible
- keeps speculative ideas visibly optional
- stays aligned with purpose, vision, and architecture

## Common Anti-Patterns

- converting every idea into a commitment
- listing detailed implementation tasks under each horizon
- organizing the roadmap by tools or frameworks instead of capabilities
- using exact dates where sequence or priority would be more honest

## Review Questions

- Could a reader tell what changes now versus later versus maybe?
- Are the entries strategic outcomes rather than task tickets?
- Does the roadmap preserve optionality for uncertain ideas?
- Is any backlog or release-management content leaking in?
- Does the sequence still align with the project's purpose and vision?
