# Selected native audio processing

Relates to #75/#78/#70/#72 and Aniflow #212. These are source implementations;
no actual installed/native/reference-meter qualification is asserted.

The existing native request/plan/approval/run/status/resume commands and public
SDK can select an installed independently pinned Aniflow row. The descriptor
must expose the exact profile and release contract. No sibling checkout or
substituted executable becomes a released provider. Candidate and authenticated
released authority modes keep their existing separate approval requirements.

For `fixed-audio-gain-v1`, select one exact current final media file and the
original closed `aniflow.audio-gain-request/v1` configuration. Explicit tools,
current QC, selected goals and gain/headroom limits remain Aniflow-owned. The
adapter checks the running descriptor, source bytes/order, complete native
request and canonical owner plan, then invokes the existing owner facade.
Current completion and exact confined output bytes must agree. The accepted
`gain_audio` artifact has purpose `audio_derivative`, never `clean_archival_master`.

Native/QC/source/tool paths selected anywhere in the configuration remain outside
the writable Flow workspace. A retained attempt is resumed only by explicit
native-run path and the original admitted intent. Uncertain or refused runs
retain their work; no automatic directory scan, fallback or fresh replay occurs.

A complete transformation does not mean the selected loudness/peak goals were
met. Gain outputs require fresh exact-file QC, a selected-policy comparison and
separate musical review. Status validates retained evidence/current artifact
bytes; it does not refresh Aniflow QC, qualify meters or grant publication.

The separately selected `final-lossless-audio-qc-v1` and
`final-video-audio-qc-v1` routes take one exact final file and the respective
existing resumable QC request. Source, full native intent and exact `qc.json`
content must agree with the returned owner report. The receipt's native run
names the QC directory and its accepted report pin supplies the separately
retained digest for a later `audio-policy-check-v1` request. These routes do not
choose a policy, transform audio or grant a numeric pass. An encoded-video check
cannot consume a WAV report as its final-byte measurement. Re-encoding after QC
requires another explicitly selected final-file check.

`gain-video-v1` selects two exact inputs in order: the original accepted picture
and the accepted adjusted WAV. Its original native request names the gain run
and fresh goal-matching WAV QC. Aniflow copies the supported H.264 picture and
encodes the selected AAC bitrate once; full original audio origin, sample count,
stereo and tails remain owner-validated. The initial plain/burned SDR, 48 kHz
mono/stereo subset and unsupported soft-subtitle/timing cases stay explicit.
Flow binds both returned lineage identities and treats `gain_video` as a
`video_delivery` derivative even if the native source variant was a clean
master. Its encoded bytes still require fresh video-audio QC and policy matching.

Delivery payloads can explicitly choose source kind `adjusted_native`, with a
`selection` containing `processing_plan`, `artifact_id`, `qc_plan` and
`policy_plan`. Each plan is an exact existing Flow native-plan FilePin. Gain
WAVs use role `audio_derivative`; adjusted video uses `video_delivery`. Both
require matching accepted final-file QC and selected-policy snapshots under
the same pinned provider cohort. The original processing input must belong to
the selected pilot, and the ordinary accepted clean master must remain selected
separately. Missing/incompatible QC or nonmatching goals refuse the selection.

Packaging copies the derivative and retained plans/configurations/receipts/owner
records, including the exact QC and policy artifacts, to a fresh private package.
It invokes no provider and never refreshes measurements. A canonical lineage
digest enters the payload's review subject: new processing/QC/policy history
requires a new supplied review even if the media bytes remain identical.
Portable package status reads copied records and payloads only. A later fresh
approved audio-readiness check is still required to assert current owner-QC
readiness; these historical package records do not establish it or qualify a
release, platform, musical review or upload.
